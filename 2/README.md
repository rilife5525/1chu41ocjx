## 1. 結論先講：大爺提的「homura / sakura 模板改配色」該不該做？

大爺的提案是：

> 男性駕駛機體 → 套 homura 的裝備外觀、改配色
> 女性駕駛機體 → 套 sakura 的裝備外觀、改配色
> 重裝又沒外觀的 → 套「灰」預設、改配色（aurum 不用改）

**我的評估：可以當「L1 墊底」，但不能當最終解。三個理由：**

### ① 它不是「每個機體都有新設計」，是「同一套設計換色」

- `homura` 的裝備外觀＝`cf5ShipUtil.drawGear`：背後虛線光輪／噴口光環／背板／副砲莢艙／核心寶石／天線陣列。
- `sakura` 的裝備外觀＝`spCommon.drawGear`：側噴口／背板／徽章光環／胸核／漂浮晶片。

兩套都是**通用幾何**（六格裝備各自對應一個制式零件）。換色之後，套到 `tetsugaki`（重裝機神）身上還是重裝機神背著一組「別人的零件」——**大爺現在覺得「突兀」的成因正是幾何不合，不是顏色不合**。換色只解決顏色那一半。

### ② 性別不是可靠的判準（而且資料裡根本沒有性別欄位）

`SHIPS[id]` 的欄位是 `id / name / en / sigil / sigilEn / pilot / pilotEn / role / color / color2 / dark / quote / lore / portrait / base / radar / activeCd / ultTime / skills / cut / cutin`——**沒有 gender**。

而且機體風格跟駕駛性別無關：`tetsugaki`（鉄平・男）重裝、`soga`（鐵山 蒼・男）重裝砲擊、`lance`（白鷺 凜・女）貫穿狙擊、`hizuki`（朱鷺沢 澪・女）弧刃突擊、`aurum`（鐵山 巖・男）重砲轟炸。用性別硬分，等於把 80 台壓成兩種，比現在更單調。

### ③ 會直接踩到「圖元索引（opIndex）」陷阱 ← 這條最致命

把 homura 的 `drawGear` 搬到別的機體，會改變該機體繪製時的**圖元總數**；而外觀編輯器的所有覆蓋（`SHIP_OVERRIDES`）**是以全域遞增的圖元索引為鍵**。索引一位移，既有覆蓋就套到錯誤的形狀上——**而且是靜默的**（不會報錯、不會崩，只是外觀壞掉）。

實測結果（見 §3）：**22 台有覆蓋的機體裡，38 組（機體 × 裝備等級）組合已經在錯位了。** 這件事現在就壞了，不是搬模板才會壞。

### 我的建議：分兩層走

| 層 | 做什麼 | 風險 | 效果 |
|---|---|---|---|
| **L1 立即** | 把「灰」的作法（見 `01` §4.2）推廣到**全部 17 個家族**：每個家族的 `drawGear` 改成「從機體色票推導同色系金屬」，而不是各家族寫死的稀有度色表 | **零**（只換顏色字串，不動圖元數量） | 解決「不合」的 8 成，80 台一次到位 |
| **Step 0** | 修好 opIndex 架構（見 `01` §5）：讓 `drawGear` 的圖元**不佔用覆蓋索引** | 中（動到編輯器 runtime，需同步改 `src/editor/overrideRuntime.ts`） | 之後任何新設計都不會再弄壞覆蓋；順便修掉現有 38 組錯位 |
| **L2 客製** | 每台機體一張「gear 主題參數表」＋一支共用主題繪製器 | 低（Step 0 完成後） | 這才是「每個機體都有新設計」 |

**如果大爺只想先看到改善**：做 L1 就好，一天內可完成，而且絕對不會弄壞任何現有設計。
**如果大爺要的是「每台都有自己的設計」**：Step 0 必須先做，否則每次新增設計都在拆自己的覆蓋表。

## 3. ⚠ 現況重大發現：覆蓋表曾經在錯位（**已於 2026-10-12 Step 0 修復**）

> **本節記錄的是「修復前」的實測結果，留著是為了說明 Step 0 為什麼必要、以及它修掉了什麼。**
> 現況：`node _gear_opidx_test.mjs --strict` → **錯位組合 0 / 88**（baseline 已更新為 0）。

**外觀編輯器的一個 `fill()`／`stroke()` ＝ 一個「圖元」，用全域遞增索引當鍵。`drawGear` 也在同一個計數器裡。**

而各家族的 `drawGear` 是**依裝備等級條件式地**決定畫幾個圖元（例如 `if (g[0] >= 3)`）。於是：

> **裝備等級一變，機體本體的圖元索引就整體位移 → 既有覆蓋套到錯的形狀上。**

實測（`node _gear_opidx_test.mjs`，用真實 `ShapeRecorder` 逐台比對 gear=0 與 gear=R）——**以下為修復前**：

| 機體 | 覆蓋 op 數 | R1 | R2 | R3 | R4 |
|---|---|---|---|---|---|
| crow / jade / prism / hien / soga / tsukikage / sumizome / rinshin / suiren / kagari / seiran / yozora / onyx | 1~3 | ✅ | ✅ | ✅ | ❌ |
| gunsei / souka / sakura / umbra / frostluna / petal / void | 1~3 | ✅ | ❌ | ❌ | ❌ |
| **hyakki** | 3 | ❌ | ❌ | ❌ | ❌ |
| marionette | 2 | ✅ | ✅ | ✅ | ✅（2026-10-12 已修） |

**修復前合計 38 / 88 組（機體 × 等級）出現錯位。**

- 原生 `shipUtil.drawGear` 家族：**只有 UR（R4）會壞**（因為 back 層要 `g[3]>=4 || g[5]>=4`）。
- `arenaCommon` 家族（gunsei/souka/hizuki/yagarasu/tetsugaki/yumei）：**R2 起就壞**。
- `cf5ShipUtil` 家族（hyakki/homura/shirayuki/kokuyou）：**R1 起就壞**（連 R 裝備都會）。

這解釋了大爺記的「`yozora` 看起來會有繪製錯誤問題」——它正是 R4 錯位那一組。

**修法**見 `01-架構與鐵則.md` §5（Step 0）——**已實作完成**：gear 圖元改記 `GEAR_OP = -1`、不佔 `opCount`，
所以**現在再新增／搬移 `drawGear` 也不會弄壞任何既有覆蓋**（L2 已解鎖）。
