## 2. `drawGear` 契約

### 2.1 簽名（各家族不同，別硬套）

```ts
// 原生（src/game/render/shipUtil.ts）— 灰機、ak5 轉出、zx/nx 補掛的都用這支
export function drawGear(ctx: CanvasRenderingContext2D, o: GearDrawOpts, front: boolean): void

// arena 家族（src/game/port/arenaCommon.ts）— 名字不同、參數也不同
export function drawGearFx(ctx: CanvasRenderingContext2D, v: AShipView, c1: string, c2: string, layer: "back" | "front"): void

// 其餘 12 個家族：drawGear(ctx, o, <front|after|over>)  ← 第三個參數的名字各家族不一樣，語意相同
```

`GearDrawOpts`（原生版）**只需要四個欄位**：

```ts
interface GearDrawOpts { t: number; thrust: number; gear: number[]; color?: string; color2?: string }
```

> ⚠ `zx`／`nx` 家族的 `ShipDrawOpts` **沒有** `color`／`color2` 欄位（型別上），
> 但 `makeOpts()` 的產物在 runtime 有 → 所以原生 `drawGear` 把它們寫成**選用**欄位。
> 新程式碼要拿機體色票，一律 `o.color ?? "#8b95a8"` 這種寫法，不要假設一定有。

### 2.2 呼叫時機（**固定兩個位置**）

每一台機體的 draw 函式都必須：

```ts
drawGear(ctx, o, false);   // ← 第一個繪製指令：畫在機體「後面」
/* …機身本體… */
drawGear(ctx, o, true);    // ← 最後一個繪製指令：畫在機體「上面」
```

這是硬約定（`src/game/port/spCommon.ts` 檔頭有寫）。**不要在中間插第三個 `drawGear` 呼叫。**

### 2.3 `o.gear` 六格語意（**順序是 SP 的，不是 arena 的**）

| 索引 | 槽位 | 稀有度 |
|---|---|---|
| `gear[0]` | 主砲／武器 | `0`＝未裝備 |
| `gear[1]` | 裝甲 | `1`＝R |
| `gear[2]` | 引擎 | `2`＝SR |
| `gear[3]` | 核心 | `3`＝SSR |
| `gear[4]` | 晶片 | `4`＝UR |
| `gear[5]` | 徽章 | |

> ⚠ **arena 家族（`arenaCommon.drawGearFx`）收到的是重排過的順序**：
> `[武裝, 核心, 裝甲, 引擎, 晶片, 護符]`。這是 `shipDrawC.ts` / `shipDrawD.ts` 的 `makeView()` 做的
> （`arenaApi.ts:96` 有註解說明）。改 arena 家族的 `drawGear` 時不要套 SP 的順序。
>
> ⚠ `cfLUtil` / `spCommon` 收到的是**物件**不是陣列：`{ weapon, armor, engine, core, chip, emblem }`
> （`GearView`／`gear.tiers`）。轉接在 `shipDrawH.ts` 的 `gearView()` / `shipDrawG.ts`。

### 2.4 座標系與尺寸

- **原點＝機體中心**，**機首朝上（−y）**，單位＝機體本地單位。
- 機體大約落在 `x ∈ ±60`、`y ∈ −65 ~ +85`（含尾焰）。
- **逐台的實測「本地範圍」在 `02` §1 總表的「本地範圍 x / y」欄。**
  那是用真實 `ShapeRecorder` 量出來的，**請直接抄**（你不需要、也無法自己量）。
- `PORT_SHIPS_076` 的 16 台：入口先 `ctx.scale(0.76, 0.76)`，所以**本地座標不用自己縮**。
- 對稱：**不要呼叫各家族的 `mirror`／`both`**（同名不同簽名，見 `03` §4.2）。
  要鏡射就自己寫：
  ```ts
  for (const s of [-1, 1]) { ctx.save(); ctx.scale(s, 1); /* 只畫 +x 半邊 */ ctx.restore(); }
  ```

#### 🔴 尺寸從哪來（L2 必看）

**`o.gw`／`o.gl`（半翼展／半機長）只有 `cfUUtil` 的 `ShipOpts` 有。** 其餘 13 個家族沒有。

所以 L2 的零件尺寸**一律由 `GearTheme` 的 `w`／`h` 帶**（見 `03` §3.2），
值就是 `02` §1 的「本地範圍」：

| `02` §1 的欄位 | 換算 |
|---|---|
| `x -34~34` | `w = 34` |
| `y -28~45` | `h = 45`（取絕對值較大者） |
| `y -42~58` | `h = 58` |

`03` §3.4 的共用繪製器用 `size(th) → { gw: th.w, gl: th.h }`，零件再以 `gw`／`gl` 的倍率定位
（例如「徽章環半徑 = `gl * 1.25`」）。這樣同一台在遊戲／縮圖／Cut-in 三個呼叫點的尺寸都一致。

### 2.5 色票

`o.color`＝主色、`o.color2`＝副色，來源是 `SHIPS[id].color / .color2`（見 `02` §1 的表）。

- **多數家族**：`shipDraw.ts` 的 `makeOpts()` 一定會塞 `color`／`color2` → 用 `shipColors(o)` 讀。
- **`spCommon`**：它的欄位叫 **`col`／`col2`** → 用 `gearColors(o.col, o.col2)`。
- **`cfLUtil`**：**完全沒有色票欄位**（只有 `id`）→ 用 `03` §1.2 的 `SHIP_C[o.id]` 特例。
- **`arenaCommon`**：色票由呼叫端以 `c1/c2` 傳入（已是機體色）。

L1 的顏色工具在 `src/game/render/gearPalette.ts`（純函式、零 import）：

```ts
import { metal, gearColors, shade, mix, rgba, shipColors } from "./gearPalette";

metal("#ff4a2b", 0.5, 0.26)   // → 取 #ff4a2b 的色相，低飽和、指定明度的金屬色
gearColors(...shipColors(o))  // → ["", R, SR, SSR, UR]
```

> ⚠ **不要**去用家族檔案裡那個也叫 `metal` 的函式 —— 那是**漸層物件產生器**，不是顏色工具
> （`spCommon.metal(ctx,x0,y0,x1,y1,a,b,mid?)`、`cfU.metal(ctx,x0,x1,a,b,c)`）。同名不同物，見 `03` §4.2。

## 3. 鐵則（違反＝靜默壞掉，不會報錯）

### 🔴 R1 — 圖元索引（opIndex）契約

**一個 `fill()`／`stroke()`／`fillRect()` ＝ 消耗一個全域遞增索引。** 覆蓋表 `SHIP_OVERRIDES` 就是以此為鍵。

而**同一條繪製流程裡的圖元會互相影響索引**：

```ts
drawGear(ctx, o, false);   // ← 這裡畫了幾個圖元，後面全部往後推
機身.fill();               // ← 索引 = drawGear 畫了幾個
機身.stroke();
```

各家族的 `drawGear` 是**條件式**決定畫幾個（`if (g[0] >= 3)`），所以：

> **裝備等級一變 → 機體本體的索引整體位移 → 覆蓋表套到錯的形狀上。**

實測（`node _gear_opidx_test.mjs`）：22 台有覆蓋的機體中，**38 / 88 組（機體 × 等級）曾經在錯位**。

> ✅ **2026-10-12 Step 0 已完成**（見 §5）：gear 圖元改記 `GEAR_OP = -1`、不佔 `opCount`。
> 現在 `_gear_opidx_test.mjs --strict` 是 **0 / 88**，下表已不適用於「新增／搬移 gear 圖元」的情境——
> 但仍適用於「**機體本體**圖元的增刪」。本節保留是為了說明 Step 0 在修什麼。

**所以（以下針對「機體本體」的圖元，不含 `drawGear` 內部）：**

| 你要做的事 | 允許嗎 |
|---|---|
| 改既有 `drawGear` 的**顏色字串** | ✅ 安全 |
| 改既有 `drawGear` 的**圖元數量**（加／刪 `fill`/`stroke`） | ✅ **Step 0 後安全**（在 `gearBegin()`／`gearEnd()` 之間就不佔索引） |
| 在**機體之前**新增圖元（含新 `drawGear` 的 back 層） | ✅ 同上（只要是 `drawGear` 畫的） |
| 在**機體本體**中間插入／刪除圖元 | ❌ 會位移機體本身的索引 → 既有覆蓋跑掉 |
| 在**機體之後（尾端）**新增圖元 | ✅ 安全（沒有東西排在它後面） |
| 用 `drawImage` / `strokeRect` / `fillText` 畫 | ✅ 不消耗索引（recorder 只算 `fill`/`stroke`/`fillRect`） |

**安全模式（Step 0 之前唯一可用的寫法，✅ 現在已不需要）：** 新設計的全部圖元都放在**該機體 draw 函式的最後面**，
且**不得改動機體之前（back 層）的圖元數量**。代價：做不出「畫在機體後面的光環／羽翼」。
→ Step 0 已完成（§5），**gear 圖元不佔索引，back 層可以做**。

### 🔴 R2 — 動到 R1 紅線時，必須先確認該機體有沒有覆蓋

有覆蓋的 22 台（**全部沒有 `sig` 幾何指紋保護**，所以位移＝直接套錯）：

```
crow jade prism gunsei souka hien soga tsukikage sumizome rinshin suiren
sakura umbra frostluna petal void hyakki kagari seiran yozora onyx marionette
```

**不在這份名單上的機體，改動圖元數量是安全的。**

### 🔴 R3 — 自訂圖元（Addon）一律用「原始 ctx」

`SHIP_ADDONS` 的圖元**不經過 recorder**。若讓它們的 `fill`／`stroke` 進到 recorder，會佔用索引、把真實圖元往後推。
編輯器已經處理好了；**手寫 addon 資料時不要繞過 `drawShipOver` 的 `drawAddons()`**。

### 🔴 R4 — 顯示倍率由入口統一處理

`PORT_SHIPS_076` 這 16 台：`dealer hari fude kaleido vesper zanshin tempus shirabe marionette tenbin pugna kiln lunate oracle papilio tether`
→ `drawShipBase` 會先 `ctx.scale(0.76)`。**不要在 `drawGear` 裡自己再乘一次。**

### 🔴 R5 — `drawGear` 必須是 `o` 的純函式

同一支 `drawGear` 會被這些地方呼叫，**參數完全不同**：

| 呼叫點 | 特徵 |
|---|---|
| `renderer.ts:500` | 戰鬥中，gear＝玩家實際裝備 |
| `cutin.ts:351` | 奧義 Cut-in，`thrust`／`alpha` 不同 |
| `shipThumb.ts:61` | 機庫縮圖，`gear` 可能是全 0 |
| `kaleido.ts:427`／`460`、`petal.ts:147`、`shade.ts:386` | 殘影／分身，`gear` **刻意全 0** |

→ 不可依賴模組層可變狀態、不可 `Math.random()` 當唯一輸入（殘影會抖）、不可寫檔／改全域。

> 註：`Math.random()` 目前 **已被既有家族使用**（`nxShipUtil.flame`、`cf*` 的 `bolt`），
> 那是為了尾焰抖動，可接受；但**不要讓幾何形狀取決於亂數**（會讓覆蓋表與測試失效）。

  寫新零件時**不要**去呼叫這些 helper，用原生 `ctx`。

### 4.1 「突兀／不搭」的成因

各家族的 `drawGear` **幾何是通用的**（六格裝備各自對應一個制式零件：側掛砲艙、肩甲、噴口、胸核、環繞星、尾鰭…），
**顏色則是各家族寫死的稀有度色表**（R＝灰藍、SR＝青、SSR＝金、UR＝紅）。

所以：
- 機體色系跟「灰藍／青／金／紅」不合 → 使用者看到的就是**大爺記的「灰」**。
- 機體輪廓跟通用零件不合（`tetsugaki` 重裝 vs `papilio` 蝴蝶）→ **「突兀／不搭」**。

**換色只解決前者。後者要靠 L2 客製（每台自己的主題）。**

### 4.2 L1：把「灰」的作法推廣到 14 個家族（零風險）

2026-10-12 已在 `render/shipUtil.ts` 做過一次，作法可整套複製：


`RecShape` 另加一個欄位，供編輯器把裝備外觀從「可編輯清單」濾掉：

```ts
/** 這個圖元是不是「裝備外觀（drawGear）」畫出來的（`ops` 會是 GEAR_OP） */
gear?: boolean;
```

> 為什麼用 `-1` 而不是「gear 圖元共用同一個 op 索引」：`shapes` 是**陣列**（不是以 op 為鍵的 Map），
> 每個 `RecShape` 各自記自己的 `ops`；用 `-1` 就天然與覆蓋表的非負整數鍵隔開，
> `entryFor()`／`effSegs()` 對 `sh.ops[last] = -1` 自然回 `null`（＝沒有覆蓋），不必另外特判。

**(b) 14 個家族的 `drawGear` 各包一層 wrapper（**不縮排、不動內文**）：**

```ts
// 原本：export function drawGear(ctx, o, front) { …整段內文… }
function drawGearImpl(ctx: CanvasRenderingContext2D, o: ShipDrawOpts, front: boolean) { …整段內文不動… }

// 新增：
export function drawGear(ctx: CanvasRenderingContext2D, o: ShipDrawOpts, front: boolean) {
  const r = ctx as unknown as { gearBegin?: () => void; gearEnd?: () => void };
  // ⚠ 兩支都要用 typeof 檢查：只檢查其中一支，tsc 會對另一支報 TS2722（possibly undefined）。
  // ⚠ 也**不可以**先解構存成常數再呼叫 —— 方法脫離 this 會在 runtime 炸。
  if (typeof r.gearBegin !== "function" || typeof r.gearEnd !== "function") return drawGearImpl(ctx, o, front);
  r.gearBegin();
  try { drawGearImpl(ctx, o, front); } finally { r.gearEnd(); }
}
```

> ⚠ `arenaCommon.drawGearFx` 的 `drawGearBack`／`drawGearFront` 是 module-private，
> 直接在 `drawGearFx` 包一層即可（它是最外層）。
>
> ⚠ 一定要 `try/finally`：`drawGear` 內有早退（`if (!g) return;`），漏了收尾會讓整台機體後續圖元全變成「gear」→ 覆蓋全部失效。

**(c) `drawShipOver` 在建立 recorder 後、呼叫 `base` 前，把 `inGear` 歸零**（防禦萬一有殘留）：
